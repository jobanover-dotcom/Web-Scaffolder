## Why this exists

Every new application starts with the same foundation questions: where does code live, how does authentication work, what is the runtime contract, what should an agent read, and which versions are compatible?

**Web Scaffolder turns those decisions into executable structure.**

The generated project is intentionally small but real: framework entry points, strict TypeScript where applicable, linting, tests, health checks where a backend exists, environment examples, CI, architecture guidance, and task-routed agent documentation.

## What Web Scaffolder does — and does not do

### Developer experience (DX)
DX belongs to the **Web Scaffolder developer using this CLI**:

- progressive stack interview
- explicit compatibility profiles
- stack capability validation
- dry-run/preview and repeatable configuration as the project evolves
- diagnostics and `doctor`
- stack extensions
- deterministic manifests and generated metadata
- agent-oriented documentation

### Generated application UX
UX belongs to the **people using the application generated by Web Scaffolder**:

- accessibility
- responsive interfaces
- navigation and interaction patterns
- loading, error, empty, and validation states
- authentication experience
- visual consistency

These are deliberately separate concerns. Improving the CLI does not automatically mean improving the generated application's UX, and generated UX requirements should not clutter the scaffolder's developer workflow.

## Prerequisites

### To run Web Scaffolder
- Node.js 24 LTS, or Docker
- No global TypeScript, ESLint, or Prettier installation is required.

### To run a generated project
Requirements depend on the selected stack. The generated project's README and `docs/guides/setup.md` contain the exact commands and runtime requirements for that selection.

## Quick start

```bash
npx web-scaffolder@latest
```

Or from a clone:

```bash
npm install
npm run doctor
npm start
```

Useful commands:

```bash
web-scaffolder doctor
npm run stack:new -- payments backend "Payments API"
npm test
```

The CLI never overwrites a non-empty destination. It stages generated files and moves them into place only after generation succeeds.

## Features

- **Multiple application families** — Next.js App Router, React + Vite, Expo Router, and backend-only shapes.
- **Backends and data services** — Supabase, PostgreSQL where supported, Spring Boot, and Laravel.
- **Styling** — Tailwind CSS or CSS Modules for web; native styling for Expo.
- **Lean agent docs** — `AGENTS.md` is always-on; `RULES.md` maps concerns to focused playbooks.
- **Architecture profiles** — Small, Medium, and Large are interpreted by each selected stack.
- **Intent-based authentication** — the interview starts from product intent rather than forcing protocol jargon.
- **Manifest-driven generation** — stack manifests declare capabilities, dependencies, environment variables, and playbooks; compatibility profiles own exact versions.
- **Runnable foundations** — selected stacks receive executable framework files, health endpoints, security defaults, tests, and build/lint/typecheck commands.
- **Safety checks** — destination guards, manifest checks, compatibility validation, and generated-output verification.
- **Stack extensions** — new technologies can follow the adapter contract and extension generator instead of modifying unrelated core logic.

## Generated project structure

Typical generated projects include:

| File | Purpose |
|---|---|
| `AGENTS.md` | Small, always-loaded instructions for coding agents. |
| `RULES.md` | Lazy `concern → playbook` index. |
| `CONTEXT.md` | Project goals, decisions, boundaries, and advisory concerns. |
| `PROGRESS.md` | Project progress tracking. |
| `playbooks/` | Selected stack and concern guidance. |
| `package.json` | Dependencies and scripts for the selected JavaScript workspace. |
| `web-scaffolder.profile.json` | Machine-readable generation choices. |
| `.env.example` | Declared environment variables with the correct client/server prefixes. |
| Framework source/config | A runnable application slice for the selected stack. |
| `.github/workflows/` | Optional generated CI. |

## Architecture

Web Scaffolder is manifest-driven. Stack manifests describe what a technology supports; compatibility profiles resolve exact versions; executable scaffolders produce the files that the manifests promise.

Adding a policy-only concern can be done through a manifest and playbook. Adding an executable technology should use the stack adapter contract, focused scaffold implementation, and contract tests. See [`docs/STACK_EXTENSIONS.md`](./docs/STACK_EXTENSIONS.md).

## Roadmap

The progressive roadmap covers CLI DX, modern generated foundations, agent-native projects, reproducibility/upgrades, generated application UX, and quality/security. DX and UX remain explicitly separated throughout the roadmap.

See [`docs/ROADMAP.md`](./docs/ROADMAP.md).

## Contributing

1. Fork and create a feature branch.
2. Run `npm install` and `npm test`.
3. Add or update a manifest for new stacks or concerns; keep exact package versions in `compatibility/profiles.json`.
4. Run the focused generated-output verification for the change.
5. Add migration notes when changing generated structure or compatibility behavior.
